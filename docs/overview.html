内部 API 认证：Kubernetes ServiceAccount Token + TokenReview

UK8s 1.18.19 测试集群实测说明 · 2026-10-21 · 代码：github.com/Andrewmatilde/k8s-sa-token-auth-demo

一句话结论术语集群现状部署拓扑 安全链路判定规则验证结果 安全边界风险与后续

一句话结论

Pod 用 kubelet 签发的、audience 绑定为 internal-api 的短期 ServiceAccount Token 调用内部 HTTPS API。服务端调用 kube-apiserver 的 TokenReview 验证 token，验证成功的结果在本地缓存 30 秒，然后按 Namespace + ServiceAccount 做默认拒绝的授权。方案不引入 Service Mesh，也不需要独立的 STS 或 JWT Issuer。

术语

术语含义
audience（aud）JWT 中的 aud 字段，表示这张 token 是签发给谁用的，也就是哪个服务应该接收它。接收方只接受 aud 是自己的 token。类比：门禁卡上写着「仅限 3 楼」，拿到 5 楼刷不开。这里业务 token 的 aud 是 internal-api，kube-apiserver 自己只认 https://kubernetes.default.svc，所以两种 token 不能互用，一张泄露也打不开另一个。
Projected SA Tokenkubelet 通过 TokenRequest API 为 Pod 申请的 token：可以指定 audience、有效期短（这里是 1 小时，自动轮换），并且绑定 Pod，Pod 删除后立即失效。挂载方式是 projected 卷中的 serviceAccountToken 源。
legacy SA Token旧式 token，保存在 SA 的 Secret 里：没有 audience、永不过期，只要 Secret 还在就一直有效。本方案不接受它。
TokenRequestkube-apiserver 签发 projected token 的 API。需要 apiserver 配置 issuer 和 signing key 才会开启；UK8s 1.18 默认没有开启。
TokenReviewkube-apiserver 提供的「帮我验一下这张 token」API。服务端提交 token 和期望的 audience，apiserver 返回是否有效以及身份（namespace/SA/UID）。验签、过期判断、Pod 是否还存在都由 apiserver 完成。
singleflight同一个 key 的并发请求只真正执行一次，其余请求等待并共享结果。这里用来保证同一个 token 的并发缓存未命中只触发一次 TokenReview。

对控制面做的改动（UK8s 1.18 默认未开启 TokenRequest）

改动前，客户端 Pod 卡在 failed to fetch token: the API server does not have TokenRequest endpoints enabled；同时，带 audiences 的 TokenReview 会返回 500 error validating audiences。处理方式是在 3 台 master 的 /etc/kubernetes/apiserver 中逐台滚动追加以下参数，每台重启后 2–3 秒 healthz 恢复正常：

--service-account-issuer=https://kubernetes.default.svc
--service-account-signing-key-file=/etc/kubernetes/ssl/ca-key.pem
--api-audiences=https://kubernetes.default.svc
  • 签名私钥沿用 controller-manager 原本签发 legacy token 的 ca-key.pem，与已有的 --service-account-key-file=ca.pem 是同一对密钥，存量 token 不受影响。
  • internal-api 故意没有加入 --api-audiences，这样内部 API 的 token 无法被 kube-apiserver 接受。
  • 每台都有备份：/etc/kubernetes/apiserver.bak-20261021-tokenrequest，可以随时还原。

部署拓扑

安全链路：一次请求的完整流程

逐步说明

  1. 签发。kubelet 代表 Pod 调用 TokenRequest，申请 audience=internal-api、有效期 1 小时的 token。apiserver 用 ca-key.pem 签名，token 中绑定了 Pod 和 SA。
  2. 落盘。kubelet 通过原子替换符号链接把 token 写入 /var/run/secrets/internal-api/token，并通过 fsGroup 让非 root 进程可读。Pod 不挂载 kube-apiserver audience 的默认 token。
  3. 取用。Client 每次请求都重新读取 token 文件，不在内存中长期保存，所以 kubelet 轮换后立即生效。
  4. 发送。只走 HTTPS，并用指定的 CA 校验服务端证书（不提供跳过校验的选项）。token 只发往白名单中的 host，跨 host 的重定向不跟随。
  5. 解析。Middleware 只接受一个 Authorization: Bearer <JWT 字符集> 头，且长度不超过 16 KiB，否则返回 401。客户端传入的 X-Namespace 之类的头一律忽略。
  6. 查缓存。Key = SHA-256(token) + audience + cluster，缓存中不保存 token 明文。命中且未过期时直接得到 Identity，不访问 API Server。
  7. 未命中。同一个 token 的并发请求由 singleflight 合并为一次 TokenReview。spec.audiences 固定取服务端配置，客户端无法指定。请求带独立的 3s 超时，不会因为某个调用方断开而取消。
  8. 校验结果。要求 status.error 为空、authenticated=true、status.audiences 包含 internal-api，并且 username 严格符合 system:serviceaccount:<ns>:<name>。
  9. 写缓存。只缓存成功结果，TTL 为 30s，从发起 review 之前开始计时，所以慢请求不会延长有效期。singleflight 返回后还会再检查一次是否已过期。
  10. 构造身份。Identity 中的 Cluster 来自服务端启动参数 -cluster，其余字段来自 TokenReview，然后放入 request context。
  11. 授权。Authorizer 每次实时按 (ns, sa, method, path) 精确匹配允许列表，默认拒绝，不匹配返回 403。授权结果不缓存，与认证缓存完全分离。

  • 服务端 SA 权限：create tokenreviews = yes；subjectaccessreviews 和 list secrets = no。
  • 服务端日志中 JWT 出现次数：0。日志只记录 ns/sa/路径和拒绝原因。
  • 单元测试 19 个全部通过（含 -race），覆盖缓存命中/过期、100 并发只触发 1 次 TokenReview、超时和 API Server 不可用时一律拒绝、token 轮换、不同 token 不共享缓存、日志不含 token 等场景；对 client-go v0.18 的 TokenReview 调用也有测试。

安全边界

能防住

  • 伪造 Namespace、SA 或 Cluster 头冒充身份
  • 拿 kube-apiserver token 或 legacy token 调用内部 API
  • 拿业务 token 访问 kube-apiserver
  • 利用 API Server 故障绕过认证（一律拒绝）
  • token 通过日志、响应或缓存泄露
  • client 误把 token 发到明文 HTTP、错误的 host 或经重定向发到别处
  • 服务端被攻破后横向扩权（只有 TokenReview 权限）

防不住 / 需要知道

  • token 被窃取后，在 1 小时有效期内可以被重放（未做 mTLS 绑定）
  • 所有用 internal-api audience 的服务之间可以互相重放 token；需要隔离时请给每个服务配置独立的 audience
  • Pod 被攻破后，攻击者能读到 token（但只能以这个 SA 的身份调用这个 API）
  • 节点被攻破后，该节点上所有 Pod 的 token 都能被读取
关于 projected token 文件权限：在 1.18 上 kubelet 把 token 文件写成 0600 root。我们没有给容器 root 权限，而是用 Pod 的 fsGroup: 65532 让 kubelet 把文件开放给这个组读取。容器进程仍是 uid 65532、非 root，同时 allowPrivilegeEscalation: false、capabilities drop ALL、根文件系统只读、基础镜像为 scratch（没有 shell）。fsGroup 只是一个普通的附加组 ID，不带来任何特权。

风险与后续

事项说明 / 建议
撤销延迟 ≤ 30sPod 或 SA 删除后，已缓存的认证结果最多还能用一个 TTL。需要更快撤销时可以调小 -cache-ttl，代价是 TokenReview 次数增加。缓存不会延长 token 本身的有效期（不读取 JWT 中的 exp）。
apiserver 参数为手工修改目前直接改了 master 上的 /etc/kubernetes/apiserver。master 重建、升级或 UK8s 下发配置时可能被覆盖。如果要推广，需要纳入 UK8s 的集群模板或升级流程，作为 1.18 集群的标准配置。
API Server 依赖API Server 不可用时，新 token 无法认证（已缓存的在 TTL 内仍可用）。这是一律拒绝策略的有意取舍。
多副本缓存是进程内的，每个副本各自做 TokenReview；有 singleflight 和 30s TTL，API Server 压力 ≈ 副本数 × 活跃 token 数 / 30s。
无效 token 不缓存为了不把 API Server 的抖动固化成拒绝，失败结果不缓存；如果担心被无效 token 刷量，可以在前面加限流。
与本地 JWKS 验签对比本地验签不依赖 API Server、开销更低，但 1.18 的 OIDC discovery 还是 alpha，需要自己分发和轮换公钥，Pod 删除后也无法撤销。当前规模下 TokenReview 更简单、更安全。
